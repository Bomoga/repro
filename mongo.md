# MongoDB Run Store

The single source of truth for the Repro pipeline. All stages (Detect, Diagnose, Repair, Verify) read and write through this store. **Every lane depends on this.** Schema is frozen — changes require discussion.

## Quick Start

```bash
# Environment setup (one time per developer)
export MONGODB_URI="mongodb+srv://user:password@cluster.mongodb.net/repro"
export REPRO_MONGODB_DB="repro"  # optional: separate database per developer

# Run the schema check (validates Mongoose models match contracts)
npm run check -w @repro/store

# Run the integration tests (requires MongoDB running or Atlas connection)
npm test -w @repro/store
```

## Connection

**Package:** `@repro/store`  
**Type:** Singleton cached connection per process  
**File:** `packages/store/src/connection.ts`

```typescript
import { getConnection } from "@repro/store";

const db = await getConnection();
// Use once per process lifecycle. Closes automatically on SIGINT/SIGTERM.
```

**Environment variables:**
- `MONGODB_URI` (required): Connection string
- `REPRO_MONGODB_DB` (optional, default: `repro`): Database name. Allows each developer to use their own database within the cluster, so parallel work doesn't interfere.

**Troubleshooting:**
- `ECONNREFUSED`: Check MONGODB_URI format and cluster IP whitelist
- `ENOTFOUND`: DNS lookup failed; check password and region
- `Authentication failed`: User doesn't exist or password is wrong
- `exceeded connection pool`: Too many open connections; close unused ones

See `ENVIRONMENT.md` for full setup steps (Atlas cluster, user, network access).

## Collections & Schemas

Five collections, each owned by one Mongoose model in `packages/store/src/models.ts`. All validate through Zod contracts in `@repro/contracts` on read and write.

### runs

**Document:** One per pipeline execution.

```javascript
{
  _id: ObjectId,           // internal; never exposed
  id: string,              // unique, generated by orchestrator
  trigger: "manual" | "schedule" | "webhook",
  target: {
    kind: "local" | "github",
    ref: string           // local path or GitHub ref
  },
  stage: "ingest" | "detect" | "diagnose" | "repair" | "verify" | "done",
  status: "queued" | "running" | "blocked" | "completed" | "failed",
  startedAt: string,      // ISO 8601
  logRef: string          // pointer to run_logs entries for this run
}
```

**Indexes:**
- `id` (unique): Used to look up one run by its ID
- `status` + `stage`: Used to find all running or blocked runs
- `startedAt`: Retention queries, cleanup

**Writes:**
- Orchestrator creates on `repro scan`
- All stages update `status` and `stage` as they run
- Only `verified` patches advance to `merged` status (section 9)

---

### findings

**Document:** One per detector finding.

```javascript
{
  _id: ObjectId,
  id: string,              // unique across all runs
  runId: string,           // foreign key to runs.id
  detectorId: string,      // "semgrep", "gitleaks", etc
  ruleId: string,          // detector's rule ID
  severity: "info" | "low" | "medium" | "high" | "critical",
  category: string,        // "vulnerability", "correctness", etc
  file: string,            // relative to Workspace.path
  lineStart: number,
  lineEnd: number,
  message: string,
  evidence: string,        // exact code snippet
  reproducible: boolean,   // only true after Executor confirms
  reproductionCommand?: string,
  createdAt: string
}
```

**Indexes:**
- `(runId, id)`: Look up findings for one run
- `reproducible`: Filter unconfirmed from confirmed
- `severity`: Ranking by impact
- `detectorId`: Per-detector analysis

**Writes:**
- Lane 2 (Detect) creates during detection scan
- Executor flips `reproducible: false` → `true` only during reproduction step (section 4 semantics)
- Never edited after creation

**Constraints:**
- `evidence` field never contains unredacted secrets (gitleaks runs with `--redact`)
- Every Finding must cite a detector that exists

---

### diagnoses

**Document:** One per root-cause grouping.

```javascript
{
  _id: ObjectId,
  id: string,              // unique
  runId: string,
  findingIds: [string],    // foreign keys to findings
  rootCause: string,
  proposedStrategy: string,
  riskNotes: string,
  model: string,           // "gemini-3.1-pro-preview", exact model ID
  createdAt: string
}
```

**Indexes:**
- `(runId, id)`: Look up diagnoses for one run
- `findingIds`: Reverse index for "which diagnoses cite this finding?"

**Writes:**
- Lane 3 (Diagnose) creates during diagnosis phase
- `findingIds` are validated at write: must exist in this run
- Schema validates: every ID in `findingIds` exists as a Finding in the same run

**Constraints:**
- `model` is literal (never a friendly name like "Pro")
- `findingIds` must be non-empty
- All Findings must be `reproducible: true` for this Diagnosis to move to Repair (section 5)

---

### patches

**Document:** One per repair attempt (including retries).

```javascript
{
  _id: ObjectId,
  id: string,              // unique
  runId: string,
  diagnosisId: string,     // foreign key to diagnoses
  diff: string,            // unified diff output of `git diff`
  filesChanged: [string],  // relative paths
  testsPassed: boolean,    // result of running project's test command
  originalFindingReproduces: boolean,  // false = fix confirmed
  reproductionOutputAfter?: string,  // Executor output after patch
  regressionFindings: [{...Finding}],  // new issues found, should be empty
  challengerVerdict: "confirmed" | "disputed",  // adversarial gate result
  challengerNotes?: string,
  status: "proposed" | "verified" | "rejected" | "merged",
  prUrl?: string           // GitHub PR URL after merge
}
```

**Indexes:**
- `(runId, diagnosisId)`: Patches for one diagnosis
- `status`: Find all verified or merged patches
- `challengerVerdict`: Filter disputed from confirmed

**Writes:**
- Lane 3 (Repair) creates with `status: "proposed"`
- Lane 3 (Verify/Challenger) updates with verdict
- Gate logic (section 5): `verified` only when:
  - `testsPassed === true`
  - `originalFindingReproduces === false`
  - `regressionFindings.length === 0`
  - `challengerVerdict === "confirmed"`
- Human merges PR → Lane 4 updates `status: "merged"`, `prUrl`

**Constraints:**
- `diff` is always `git diff` output, never paraphrased
- `diff` applies cleanly with `git apply` against `Workspace.headCommit`
- `status` only flows: `proposed` → `verified` → `merged`, or stops at `rejected`
- Rejected patches stay in the store (for audit)
- `regressionFindings` is empty list if no new issues found

---

### run_logs

**Document:** One per log entry (prompts, tool calls, results).

```javascript
{
  _id: ObjectId,
  runId: string,           // foreign key to runs.id
  at: string,              // ISO 8601 timestamp
  kind: string,            // "system_prompt", "tool_call", "tool_result", "model_output"
  entry: {...}             // the raw entry (prompt text, tool def, result object, etc)
}
```

**Indexes:**
- `runId`: Get all logs for one run
- `(runId, at)`: Ordered log for one run
- `kind`: Filter by entry type

**Writes:**
- Lane 3's Gemini wrapper writes after every model call (section 5)
- Never edited, only appended

**Constraints:**
- Required by section 9: every interaction's full prompt and tool-call log is retained
- Used for debugging: "why did Gemini do that?"
- Never exposes secrets: wrapper redacts API keys before logging

## Query Helpers

All in `packages/store/src/queries.ts`. These enforce the storage rules (section 4 semantics).

### Run Queries

```typescript
// Get one run by ID, fully loaded with findings, diagnoses, patches
getRunDetail(db, runId: string): Promise<RunDetail>

// List recent runs with status summaries
listRuns(db, options: { limit?: number; status?: string }): Promise<Run[]>

// Get run and all its logs (for replay/audit)
getRunWithLogs(db, runId: string): Promise<{ run: Run; logs: RunLogEntry[] }>

// Update run status/stage
updateRunStage(db, runId: string, stage: string, status: string): Promise<void>
```

### Finding Queries

```typescript
// Get all findings for one run
getRunFindings(db, runId: string): Promise<Finding[]>

// Get confirmed findings only
getConfirmedFindings(db, runId: string): Promise<Finding[]>

// Update reproducibility (Executor writes this)
confirmFinding(db, findingId: string, reproductionOutput: string): Promise<void>
```

### Diagnosis Queries

```typescript
// Get all diagnoses for one run
getRunDiagnoses(db, runId: string): Promise<Diagnosis[]>

// Validate: all findingIds exist in this run and are confirmed
createDiagnosis(db, diagnosis: Diagnosis): Promise<Diagnosis>
  // Throws if validation fails
```

### Patch Queries

```typescript
// Get all patches for one diagnosis
getDiagnosisPatches(db, diagnosisId: string): Promise<Patch[]>

// Create patch with validation
// Throws if status isn't "proposed" or diagnosisId doesn't exist
createPatch(db, patch: Patch): Promise<Patch>

// Update patch status through the gate
// Enforces: proposed → verified → merged only
// Blocks illegal transitions
updatePatchStatus(db, patchId: string, newStatus: string): Promise<void>

// Mark patch merged after PR merges
mergePatch(db, patchId: string, prUrl: string): Promise<void>
```

### Log Queries

```typescript
// Append log entry
logEntry(db, runId: string, kind: string, entry: unknown): Promise<void>

// Get all logs for a run
getRunLogs(db, runId: string): Promise<RunLogEntry[]>

// Get logs of one kind (e.g., all "tool_call")
getLogsByKind(db, runId: string, kind: string): Promise<RunLogEntry[]>
```

## Validation & Drift Detection

**Contract as source of truth.** Every write validates through the Zod contract before hitting Mongo.

**Drift detection:** `packages/store/test/models.test.ts` runs on every build. It:
1. Compares every contract field to the Mongoose schema
2. Checks every schema field is in the contract (no extras)
3. Validates enum values match exactly

If a contract gains a field and the schema doesn't, the test fails and the build blocks.

**Strict mode:** Mongoose `strict: "throw"` means writes with extra fields reject outright, not silently drop. This is intentional.

## Secrets Handling

**Never leaks secrets into the store.**

- `evidence` field: gitleaks output is `--redact`ed, so secret values never appear
- Patch `diff`: Can contain deleted secrets (the line being deleted), but that's the actual evidence of the breach; it's stored as-is per section 4
- Logs: Gemini wrapper redacts API keys before writing `entry`

See section 9 (Safety rails) for the full story.

- Uses default database name `repro`

## Troubleshooting

**"ValidationError: xxx cast to undefined"**  
→ Zod validation failed before write. Check the contract matches what you're writing.

**"E11000 duplicate key error"**  
→ ID collision. Check that IDs are unique per collection (orchestrator's job for runs, detector's for findings, etc.)

**"Timeout connecting to MongoDB"**  
→ Network access list in Atlas. Add your IP or use `0.0.0.0/0` for development.

**"exceeded connection pool"**  
→ Too many open connections or connections not closing. Check that Mongoose connects once and reuses.

**Tests pass, prod fails**  
→ Env var mismatch or permissions issue. Run `npm run check -w @repro/store` to validate schema.

## Architecture Decision Record

**Why Mongoose, not raw MongoDB driver?**  
- Schema validation (Zod) happens in code, Mongoose enforces in storage
- Automatic index management
- Connection pooling
- Query helpers reduce boilerplate in Diagnose/Repair/Verify stages

**Why Zod + Mongoose (dual validation)?**  
- Zod is the contract (TypeScript types, immutable reference)
- Mongoose is the storage layer (index, connection, enum enforcement)
- Dual validation catches drift: if contract and schema diverge, tests fail loudly

**Why @repro/store as a separate package?**  
- Isolation: store doesn't leak into contracts or agent logic
- Clear boundary: every stage knows it goes through the store
- Testing: can mock the store in Lane 3's unit tests without touching MongoDB

**Why five collections, not embedded?**  
- Findings are large (evidence can be long code snippets); embedding in runs would bloat every query
- Patches embed regressionFindings (full Finding objects) because that's rare and valuable for the verdict
- Logs are appended frequently; separate collection avoids locking the run document
